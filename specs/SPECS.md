# SPECS — the SDD contract for the `/ds:*` plugin (4 stages)

**Status:** v2.1 (2026-10-06). Normative. Per-stage gap detector, panel-built technicals, verb grammar (`docs/UX-AND-EXECUTION.md` v0.3). Templates in `templates/specs/` and `templates/deliverables/`.

## 0. Roles, cycle, verdicts, registry, manifests

### 0.1 The four artifacts (spec-driven development)

| Artifact | Role | Must contain | Must NOT contain |
|---|---|---|---|
| **Functional** `functional.md` | **WHAT** | purpose tied to project sections · inputs · deliverables promised · acceptance criteria · `must_ask` questions · constraints · gaps table | methods, tools, tasks |
| **Technical** `technical.md` | **HOW** | operational definitions · design decisions with rationale and cards applied `{id, hash}` · method and conventions · verification checks (DoD) each with `verification: test:<path> | reviewer | user` · risks | deliverable lists, schedules, cost limits |
| **Plan** `plans/<n>.md` | **EXECUTION** | hypothesis (numeric, falsifiable) · inputs with pins · ordered tasks (owner, action, input → output) · expected outputs · acceptance rule · limits · not-in-scope · decision table | design rationale |
| **Build** `builds/<n>.md` + code | **THE WORK** | code/scripts/configs/tests (path, purpose, how to run) · validation report (DoD + plan acceptance, PASS/FAIL + evidence path + hash; `[test]` items executed by `dsx dod --run`, `[reviewer]` items judged by the reviewer agent) · dispatch record · result and interpretation (for Experiment, `dsx` precomputes accepted/rejected vs the noise threshold) · verdict | changes to WHAT/HOW (those are verdicts) |

Stage functionals start as a skeleton generated by `dsx spec gen` (purpose, inputs, deliverables, acceptance, constraints derived from this document and the cited project sections) and are completed by the **stage gap detector**: schema slots + gap-detector cards + candidate questions proposed by the panel (`dsx gaps propose` → one call per consulted expert → `dsx gaps merge`), asked in waves of ≤ 4 on the main thread; answers land in a hashed `## User knowledge` section and the functional becomes `approved_by: user`. Technical specs are **built by the panel**: contributors return section contributions and DoD candidates in parallel, the lead expert drafts the full file and logs accept/reject (`panel_log`); the user is not asked unless they run `/ds:spec --technical "instruction"` (senior persona confirms). Plans consult only the experts named by the technical's `§Method` owners (cap 2); builds dispatch tasks to their `owner`. Build headers are written by `dsx build finish`, never by hand. Model and effort per call point: `docs/MODEL-POLICY.md`.

### 0.2 The cycle (stages 2–4) and verdict vocabulary

```
FUNCTIONAL (generated) ─► TECHNICAL ─► PLAN ─► BUILD ─┬─ iterate         → next PLAN
                                                     ├─ change_method   → TECHNICAL v+1
                                                     ├─ change_purpose  → project.functional v+1 (section edit; staleness per edge table)
                                                     ├─ back_to:<stage> → reopen an earlier stage's cycle
                                                     ├─ escalate        → user decides with best-so-far
                                                     └─ done + DoD met  → GATE (manifest + human decision) → next stage
```

The generated DoD decides exit; the verdict proposes. `done` with unmet DoD is forced to `iterate`. Budgets nest: plan ≤ stage ≤ project.

### 0.3 Stages and gates

| # | Stage | Cycle | Gate — who decides |
|---|---|---|---|
| 1 | **Business** (`--business`) | dialogue only, **no data** (no files, no profiling) | user: "is this the problem?" |
| 2 | **Data** (`--data`, alias `--eda`; understanding + EDA + feature understanding) | full cycle; plan 1 = profile + target rule; plan 2+ = analyses | user answers `must_ask`; DoD rows machine-checked: "does the data support it?" |
| 3 | **Modeling** (`--modeling`, alias `--experiment`; folder `03-experiment`; feature engineering + modeling + evaluation exit) | full cycle; iteration = (`features/v<k>`, method, protocol P); evaluation is the mandatory exit phase | business owner: ship / iterate / stop |
| 4 | **Ship** (`--ship`, alias `--deploy`; deployment + monitoring + handoff) | full cycle | user + named ops owner: accept handoff |

Persona changes wording and wave limits, never gates.

### 0.4 Deliverable registry (project-level nodes)

Deliverables are not buried in a stage's technical spec; they are registered nodes in `specs/deliverables/` with `{id, producer_build, version, content_hash, consumers[]}` maintained by `dsx`. v1 registry: `data_card`, `target`, `eda_report`, `feature_inventory`, `split_recommendation`, `protocol_P`, `features/v<k>`, `results_table`, `champion`, `business_metric`, `deploy`, `monitoring_config`, `model_card`.

Dependency edges are owned by `dsx` (static table + registry); headers carry only version pins written by `dsx pin`.

### 0.5 Gate manifest

`dsx gate approve <stage>` writes `specs/<stage>/manifest.yaml`: every DoD item → `{result, enforced_by: test|reviewer|user, evidence_path, sha256}`; pinned input hashes (project sections, deliverables, data hash, env lock); card-set hash; approver and persona; `accepted_stale` pins with notes. Gates certify evidence, not consent.

## 1. Business — dialogue only

**Deliverable:** `specs/project.functional.md` (the WHAT of the whole project). Sections: 1 Decision · 2 Unit of prediction and target · 3 Success criteria (a business metric + threshold, b proxy metric and the **translation formula** from proxy to business units, c baseline to beat, d ship/stop) · 4 Costs and constraints · 5 Scope · 6 **Data expected** (what the user believes exists: sources, grain, period, owner, caveats, in prose, unverified) · 7 Assumptions (`confirmed_by_user | safe_default`) · 8 Gaps table · 9 Consumers and deployment intent · 10 Change log. Header carries a **provenance block**: `requirements_schema: {id, hash}`, `cards_set_hash`, `persona`, `waves: [decisions.log ranges]`.

**Construction (skill `ds-dialogue`, main thread):**
1. `dsx init` creates the workspace and an empty functional from the template.
2. Intake: raw ask recorded verbatim. **No data is read in this stage**: no file paths, no profiling; the user only describes the need.
3. `analyst` returns `{persona, family, domain, confidence}`; one-line confirmation with the user.
4. `dsx schema select <family> <domain>` → **slot list** = base schema (`schemas/<family>.yaml`) + domain questions from cards with `enforce: gap_detector`, stage `business`. Each slot: `id · section · question · why_it_matters · source_priority (user|data|default) · default`.
5. `analyst` pre-fills slots from the ask + glance (`{slot, value, source, confidence}`); confirmed values go into sections; the rest become gaps.
6. Gap classification (deterministic + persona policy): `must_ask` · `pending_data` (to be asked by the Data gap detector or answered by Data plan 1 profiling) · `safe_default`.
7. Question waves: `dsx wave next` picks ≤ 4 open `must_ask` by `why_it_matters`; asked via `AskUserQuestion`; answers written to sections + gaps; wave logged to `decisions.log`. Loop until no `must_ask` or the persona wave limit → escalate with stated assumptions.
8. `dsx validate`: sections 1–5 filled; threshold numeric; proxy metric defined; no open `must_ask`; consistency (horizon vs cadence, grain vs unit).
9. Gate 1: `writer` renders the one-screen "problema vigente"; approve / change / stop; `dsx gate approve 1` writes the manifest, moves the cursor to 2, chains the free Data skeleton, and prints `Next: /ds:spec --functional --data`.
10. `pending_data` gaps are asked by the Data gap detector when they need no data, or closed by Data's plan 1 in one batched wave after profiling (functional v2, §7/§8 only, no re-gate). Only a §2 change reopens Gate 1.

**Gate 2 DoD ("does the data support it?"):** all `[test]` items pass · `must_ask` closed · inventory complete · split recommendation written · manifest pins data hash and deliverable hashes.

## 3. Experiment

| | Content |
|---|---|
| **WHAT** (generated functional) | **Purpose:** a champion that meets project §3 under protocol P with a point-in-time-certified feature set, translated to business units, within budget and constraints. **Inputs:** `feature_inventory`, `split_recommendation`, `target`, project §1 §3 §4. **Deliverables:** `protocol_P` (frozen at iteration 1), `features/v<k>` with `pit_certified`, `results_table` (benchmarks + candidates, per horizon/segment, with spread), `champion` (registry `staging`), `business_metric` + error analysis + calibration/coverage where relevant. **Acceptance:** every feature set used is certified; champion beats every mandatory benchmark by > noise; threshold met or budget exhausted with best-so-far; constraints satisfied (latency, interpretability, excluded variables absent); business metric computed from logged predictions by the evaluator; reproducible. **Gap detector (panel: developer + evaluator):** budget confirmation; excluded model families; missing cost inputs; segments that matter most; tolerance for complexity vs accuracy. |
| **HOW** (technical; **panel:** lead developer, contributors evaluator + reviewer) | **Definitions:** **protocol P** = split scheme mirroring deployment (rolling-origin origins/horizon/gap · group/stratified folds · temporal with maturity gap), primary metric from project §3b, benchmarks, segments/horizon buckets, seeds/repeats, noise threshold — registered as deliverable `protocol_P`; allowed feature universe (inventory rows with `available_at_inference ≠ no`, `leakage_risk ≠ confirmed`, not excluded); champion selection rule (metric → constraints → simplicity); operating point / threshold rule. **Design decisions + cards:** transformation families and constraints (min lag ≥ lead time; encoders/imputers fit inside fold; entity baselines strictly past); feature versioning (parent + diff); candidate ladder with climb rule; hyperparameter policy; imbalance policy (class weights + threshold; never resample validation); reproducibility conventions (seeds, data hash, env lock, MLflow naming); experiment budget and stop rule; evaluation exit: translation formula from project §3b, error analysis by segment/horizon/worst cases, calibration or interval coverage. **Verification checks (DoD):** `local.S3.pit-certified [test: tests/test_point_in_time.py]`, `local.S3.fit-inside-fold [test]`, `local.S3.excluded-vars-absent [test]`, `local.S3.benchmarks-same-folds [test]`, `local.S3.split-valid [test]`, `local.S3.metric-as-specified [test]`, `local.S3.reproducible [test]`, `local.S3.threshold-or-budget [test]`, `local.S3.business-metric-vs-threshold [test]`, `local.S3.evaluator-independent [test: evaluator run id ≠ developer run id]`, `local.S3.sensitivity [reviewer]` + reviewer/evaluator cards mapped to stage 3. **Certification rule:** `dsx dod` sets `features/v<k>.pit_certified = true` only when the point-in-time test passes; `dsx dispatch` refuses a training job on an uncertified feature set. |
| **EXECUTION** (plan) | **Iteration n = (features v<k>, method, P).** Hypothesis: "(v2 lags 1–8, LightGBM global, P) beats current best by ≥ X MASE at h=1..12." Tasks: 1 features v<k> (developer) → certification test; 2 train + backtest → MLflow run; 3 compare vs current best → results row; 4 update champion. **Exit iteration (evaluation):** hypothesis "champion yields business metric ≥ threshold with ≤ Y downside in the worst segment"; tasks: translation (evaluator, from logged predictions) → error analysis → calibration/coverage → sensitivity → recommendation. **Not in scope:** serving code. **Decisions:** won → next rung; lost → next rung or stop; protocol wrong → `change_method`; inventory doubt → `back_to:2`; budget out → `escalate`; evaluation go → `done`; conditional → `iterate`; no-go → `escalate`. |
| **BUILD** (the work) | **Code:** `features/v<k>/build_features.py` + `FEATURES.md`, `tests/test_point_in_time.py`, `src/experiment/backtest.py` (P implemented once), `benchmarks.py`, `experiments/<n>/run.py` + `config.yaml`, `registry.py`, `src/experiment/evaluate/translate.py`, `error_analysis.py`, `calibration.py`, `sensitivity.py`; tests `tests/experiment/test_split_validity.py`, `test_metric.py`, `test_translate.py`. **Validation:** smoke run on a sample from a clean venv; all `[test]` items; reviewer JSON with evidence paths. **Dispatch:** full run id. **Result:** results table; hypothesis verdict; champion and why; business metric vs threshold; go / no-go / conditional; risks. **Verdict.** |

**Gate 3 DoD ("ship / iterate / stop", business owner):** certified feature set · benchmarks on identical folds · reviewer PASS on champion · business metric vs threshold by an independent evaluator · manifest pins P hash, feature hash, run id, env lock, cost inputs, §3b hash.
